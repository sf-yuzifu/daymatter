# 同步与兼容说明

本文说明倒数日快应用与 AstroBox 配套插件的通信行为、版本边界和已知限制。描述以当前代码为准；本地模拟与跨语言测试不能代替真实宿主和设备验证。

相关文档：[项目 README](../README.md) · [事件数据模型](event-model.md) · [配套插件](https://github.com/sf-yuzifu/Daymatter-AstroBox-Plugin)

## 1. 平台与版本要求

- 快应用包名：`com.yzf.daymatter`；当前版本 `2.1 / 21001`。
- 当前插件使用 API Level 4、WASI 3，构建目标为 `wasm32-wasip2`。
- 仅支持 API Level 2 / 3 的 AstroBox 宿主无法加载当前插件。
- 具体最低 AstroBox 语义化版本尚未核实，应以宿主报告的 API Level 4 能力为准。
- 当前未取得经过校验的 Level 2 回退插件包，不能将旧宿主回退描述为已交付能力。

版本号不代替能力协商。插件每次业务发送先执行 `hello` 握手，按腕端明确确认的能力启用功能。

## 2. 新旧端组合

| 组合 | 当前行为 | 验证范围 |
| --- | --- | --- |
| 当前插件 + 当前腕端 | 握手回显 `handshakeId` / `deviceId`，按能力启用稳定 ID、保存回执、列表身份与分批 | 已有跨语言脚本验证；真实宿主往返仍需测试 |
| 当前插件 + 不回显握手身份的旧腕端 | 约 2 秒后使用旧业务模式；兼容新增、旧下标命令及整包列表；带 ID 写操作因能力未确认而停止 | 已测旧命令形态，具体旧产物组合仍需测试 |
| 旧插件 + 当前腕端 | 保持旧命令和整包列表，增量字段兼容返回 | 无请求身份的命令不具备新协议幂等保证 |
| API Level 2 / 3 宿主 + 当前插件 | 插件不能加载 | 需要独立、经过校验的旧插件产物 |

旧端没有请求身份时，无法区分同一接收窗口内的全部迟到回包；兼容接收不等于强一致性。

## 3. 能力协商

每次握手使用独立 `handshakeId`，匹配当前会话与目标设备。等待上限约 2 秒，迟到能力不会改变本次已确定的发送模式。启动、注册与协商准备阶段总超时为 15 秒，不清除已经发出的未知结果写操作。

| 能力 | 用途 |
| --- | --- |
| `stableId` | 按稳定 ID 修改、删除或移动，未确认时不把带 ID 操作静默退回下标 |
| `requestId` + `mutationResult` | 两项均确认后启用写请求身份和保存结果回执 |
| `listRequestId` | 列表请求身份与快照关联 |
| `listBatches` | 配合列表身份启用有界分批 |
| `yearlyRepeat` / `displayUnit` | 年度重复和每事件显示单位 |
| `pinned` / `category` / `archived` | 置顶、分类和归档字段 |
| `manualOrder` / `sortMode` | 同组移动与排序模式持久化 |
| `primaryMutation` | 独立设置/取消表盘主事件；还要求 `primaryId`、稳定 ID 与保存回执能力 |

新增字段未确认能力时，插件只省略缺省值，拒绝非缺省值及相关新操作，并提示更新腕端。旧客户端修改未携带的新字段由腕端保留。颜色和未知事件扩展也由腕端保留，插件读取模型保留扩展，但传输受预算限制。

`moveEvent` 使用稳定 ID 并复用请求账本、回执与查询；`setSortMode` 保存顶层模式。整包 / 分批列表与排序回执携带 `sortMode`。

`setPrimary` 只修改已保存事件的主事件引用，不提交插件编辑草稿。设置携带目标 `id`；取消携带空 `id` 和 `expectedPrimaryId`，腕端在提交队列中核对当前引用，不一致返回 `PRIMARY_CHANGED`。成功回执携带最终 `primaryId` / `revision` 和主事件、表盘文件分项；插件据此更新标记。旧腕端未确认该能力时拒绝发送。

## 4. 保存确认与超时处理

**消息发送成功不等于腕端保存成功。** 新协议使用 `requestId`、`sessionId`、`deviceId` 关联请求，腕端提交后返回 `mutationResult`，分别报告事件、主事件和表盘同步结果。

- 事件已保存、表盘同步失败时不应重复新增，应核对派生同步结果。
- 请求超时后查询原请求，查询不会重新执行增删改。
- `processing` 表示仍在处理，`unknown` / `expired` 不表示失败或成功。
- 原结果未知或查询无响应时，先取得同设备的新完整列表，核对后显式结束等待；这一操作不冒充保存成功回执。
- 新协议列表刷新不会解除未确认写操作的锁；旧协议写操作同样需要显式核实。
- 含异常跳过项的快照不能用于结束未知等待。

腕端在途与完成账本最多 32 条，满额明确拒绝，下一次显式操作更换会话。幂等只覆盖当前应用进程和保留的会话记录，不跨应用重启或已释放的记录。

## 5. 设备、列表与草稿隔离

操作启动前固定目标设备，修改 / 删除核对列表所属设备；原请求未结算时不能借另一设备核实。JSON 内的 `deviceId` 只用于关联，当前接口没有可信发送方来源地址，不能把它当作认证。

新协议列表按请求、会话、设备及 `revision` 校验。新拉取、超时或已经完成请求的迟到回包不会覆盖当前快照。刷新保留未提交草稿与有效页码。

| 约束 | 上限 / 行为 |
| --- | --- |
| 列表接收窗口 | 8 秒 |
| 分批列表 | 每批最多 16 条、8 KiB；完整验证后才切换快照 |
| 累计列表预算 | 256 KiB、200 条 |
| 插件消息预算 | 256 KiB，以 UTF-8 字节计 |
| 腕端入站 JSON 预算 | 262144 个 UTF-16 单元，与插件字节预算不是同一计量 |
| 旧下标快照 | 60 秒后过期，需重新同步 |

乱序和相同重复批次允许接收，缺批、异载荷冲突或超预算保留旧列表与草稿。旧下标对应内容变化时撤销选择并保留草稿；即使未超过 60 秒，旧端并发重排仍可能使下标失效。

名称校验见[事件数据模型](event-model.md)。两端需同时更新才能保证相同 Unicode 码点规则，旧腕端可能仍按 UTF-16 长度限制 emoji 名称。

## 6. 背景上传的已知限制

背景上传尚不具备与事件提交相同的保存确认机制：

- 插件生成最长边 450 px、不超过 100 KiB 的 JPEG，腕端当前仍按 `.png` 后缀保存和扫描。
- `backgroundJpeg` 能力声明不代表所有目标固件的 JPEG 显示均已验证。
- 腕端当前先删除旧背景再写新图，解码或写入失败不能保证保留旧背景。
- 插件先完整解码再缩图，输出尺寸 / 字节限制不能替代输入文件、像素和解码分配预算。
- 事件回执或列表核实不能证明背景已落盘或可显示。

这些是当前实现边界，后续需补齐保存后替换、格式一致性、解码前预算及背景结果确认。

## 7. 验证范围与复现入口

| 范围 | 现有验证 | 仍需验证 |
| --- | --- | --- |
| 请求身份、去重、回执与查询 | 腕端页面模拟、插件状态机与跨语言编码回归 | 宿主异步重入、真实收发、断连与切换 |
| 列表身份、分批与预算 | 乱序、重复、冲突、超限及迟到消息回归 | 实际传输预算与旧版本产物组合 |
| 输入草稿与 UI 刷新 | 输入只更新草稿，根树指纹去重，刷新保留草稿 | 宿主焦点、下拉框、按钮、对话框和状态刷新 |
| 设备与表盘 | 日期、存储和派生文件本地回归 | 多屏触控、固件文件行为、真实表盘与内存表现 |

验证代码位置：

- `tools/test-ime.cjs`：腕端页面、协议、异步存储和生命周期模拟。
- `tools/protocol-bridge.cjs` 与插件 `src/cross_protocol_tests.rs`：Rust 编码请求 → 腕端实际页面脚本 → Rust 解码与状态机。
- 插件 `state` / `protocol` / `view` 测试：身份、乱序、预算、草稿与动作映射。

跨语言测试需要 Node.js，并要求插件仓库的相邻目录 `../daymatter` 中存在快应用仓库。在插件目录执行：

```bash
cargo test --target x86_64-pc-windows-msvc
```

该命令使用 Windows native 目标；其他平台需选用可用的 native 目标。构建和测试通过不能推定宿主渲染或所有设备兼容性通过。报告问题时请记录设备、固件、两端及宿主版本、数据规模、步骤与日志。
