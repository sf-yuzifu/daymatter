# 农历支持可行性评估

评估日期：2026-10-08；实施更新：2026-10-09。**轻量离线查表已接入腕端与插件，提供农历输入和年度重复；多屏/宿主/真机仍待验收。** 以下评估数据保留最初候选表结果。

## 当前实现

- 表版本 `dm-hko-v1`：2057 位表27424→27296，2097位表42192→41680，调整相邻月份大小而不改变全年长度。
- `node tools/evaluate-lunar.cjs --runtime --hko`：修正版73412天往返，9个抽样年逐日全部一致；仍未完成所有年份官方核对，ICU差异仍保留为参考。
- JS/Rust运行表逐项一致，Rust全范围往返；具体字段与已采用规则见[事件模型](event-model.md)。
- 两端默认采用闰月回退普通月、三十回退月末。切换历法保持同一天，原始日期校验不允许输入不存在的闰月或三十。
- 当前release RPK测量200345 B（195.6 KiB），88文件；未保存同参数农历接入前产物，不能将与历史包差额全部算作农历增量。

## 1. 方案比较

| 方案 | 结果 |
| --- | --- |
| 设备 `Intl` 中国历 | 不作为运行依赖。Node 可用不证明 Vela/JSC 或 WASI 可用，不同 ICU 版本也可能产生不同结果 |
| 完整农历 / 黄历库 | 能力多于需求，增加节气、干支等代码和数据；首版不需要 |
| 年份位表 + 公历日序号 | 推荐。每年编码月份大小和闰月，整数运算，离线、确定性、易移植 Rust |
| 联网换算或只由插件换算 | 不满足腕端离线新增及未来年度自动计算，不推荐作为基础 |

候选数据使用 `yize/solarlunar` 的年份表，固定提交 `b1d43280119a448dbf557dfdcf73fc6f7f59f422`。本仓库评估工具保留其 ISC 许可；转换原型自行实现，不直接接入上游完整转换函数。年份表的最早来源说明包含 JJonline，正式集成前继续核对出处与版本记录。

## 2. 范围与实测

表覆盖**农历年 1900～2100**，完整月份对应公历 **1900-01-31～2101-01-28**。农历年范围与公历范围不能混写。现有公历 0001～9999 能力保持，新增农历只接受明确有数据的范围，不越界推算。

运行 `node tools/evaluate-lunar.cjs --source --hko`，本次结果：

- 201 条年份数据与固定上游逐项一致。
- 全范围 **73,412 天双向往返通过**；这是自洽验证，不代表独立准确性验证。
- 与 Node v26.9.0 / ICU 78.3 中国历比较，**477 天不同**，最早示例为 1917 年闰月归属差异。不能把 ICU 作为唯一标准。
- 与香港天文台文字年表逐日比较：2020、2023、2025、2026、2033、2089、2100 共 7 个抽样年无差异。
- 2057 年 9 月 28 日～10 月 27 日、2097 年 8 月 7 日～9 月 5 日各 30 天与天文台相差一天。
- 闰四月（2020-05-23）、闰二月（2023-03-22）、闰六月（2025-07-25）、2026 春节（2026-02-17）和 2033 闰十一月（2033-12-22）锚点通过。
- 不存在的闰月、下界前一天、上界后一天明确返回无效。

香港天文台也明确说明，远期新月接近午夜时可能存在一日预测差异，列出 2057、2089、2097 等特殊日期。正式数据建议以天文台对应日期表为验收口径，记录差异与修订；不能无说明地混用 ICU 与候选位表。**本次没有修改候选原表，也没有完成 200 年官方逐日核对。**

## 3. 包体与运行成本

| 数据表示 | 本次测量 |
| --- | ---: |
| 201 个 `u32` 原始存储 | 804 B |
| 紧凑十进制 JS 数组源码 | 1,215 B |
| 紧凑十六进制 JS 数组源码 | 1,427 B |
| 十进制数组 raw DEFLATE | 479 B |
| 十六进制数组 raw DEFLATE | 491 B |

以上只测**年份表**，不是完整功能的 RPK 或 WASM 增量。转换算法、日期选择 UI、四份语言文件、校验和协议也会增加包体，需正式接入后以相同 release/JSC 参数测量。没有据此给出未经构建的“功能只增加几百字节”结论。

最多扫描 201 年及 13 个月；可缓存年份起始日，排序时预计算事件发生日，避免比较器反复转换。普通 JS 数组实际堆占用大于 804 B，Node 计时/内存不等于手环原生表现。表与算法放共享模块，两端从同一版本数据生成，避免手工维护两份。

## 4. 建议数据模型

保持 `date` 是**原始发生日对应的公历日期**，不能把“农历 2020-08-15”直接写进现有 `date`。新增字段建议：

```json
{
  "date": "2020-10-01",
  "calendar": "lunar",
  "repeat": "yearly",
  "lunarDate": {"year": 2020, "month": 8, "day": 15, "leap": false},
  "lunarLeapPolicy": "regularFallback",
  "lunarShortMonthPolicy": "lastDay"
}
```

- 缺少 `calendar` 等价现有公历，旧事件不迁移为农历。
- **公历单次**：只按 `date`，即使界面用农历辅助选日，保存后仍是一次固定公历日期。
- **农历单次**：保存完整农历年月日及对应公历原始日期，不滚年。
- **农历年度重复**：每年按 `lunarDate` 的月、日、闰月规则换算，不能重复 `date` 的公历月日；周年数按农历发生年份减原始农历年份。
- 当前/下次公历发生日是派生值，不覆盖 `date` 或 `lunarDate`。
- 输入原始日期必须真实存在，不把原始小月三十偷偷改成二十九。年度目标月没有三十时才按明确重复策略处理。

这些字段已采用；实现额外保存 `lunarTableVersion=dm-hko-v1`。

## 5. 闰月与重复策略建议

1. 普通月生日只在普通月发生，即使当年存在同名闰月，也不再触发一次。
2. 闰月生日原始 `leap=true`。建议默认：当年有该闰月用闰月，否则回退普通同月；界面需清楚说明。
3. 可选“只在同闰月发生”：跳过没有该闰月的年份，最多搜索到表的上界，不无限循环；该选项可后续再加。
4. 年度农历三十遇小月，建议用该月最后一天二十九，保留原始三十，不把事件改名为二十九。
5. 当天仍算本次，次日滚到下一次；含首日只影响展示，不改变发生日、排序或近期筛选。
6. 超出换算范围或找不到下次发生日，显示明确不可计算状态，不能像当前通用兜底那样退回旧公历日期继续倒计时。

默认闰月回退与三十回退是产品规则，已按用户授权采用，不是历法自身唯一规定。

## 6. 两端、备份与表盘接入

- 腕端新增历法选择和农历年月日选择，闰月只在对应年份提供；显示对应公历日期供核对。农历与公历切换需定义是否保持同一天。
- 插件复用相同位表，在纯逻辑层校验和计算；宿主表单不承担换算。
- 新能力建议分别为 `lunarDate`、`lunarYearly`，并声明表版本和范围。未确认不发送农历非默认字段，不静默当公历保存。
- 旧插件修改名称等未传农历字段时保留；日期字段单独修改涉及历法语义，需显式拒绝或定义清除农历规则，不能留下矛盾的双日期。
- JSON 备份必须校验农历字段及原始公历映射，新腕端拒绝不支持的表版本。当前备份“保留未知扩展”不能视为已支持农历恢复。
- 首页、列表、临近排序、今天/未来30天及表盘共用同一发生日入口。
- `date.txt` 格式保持公历，输出农历事件对应的本次/下次公历发生日。应用退出后的后台更新保证不变，不能随农历功能宣称自动提醒。

## 7. 建议实施顺序与验收

1. 固定历法数据口径、范围和闰月/小月策略，补齐官方年表核对和差异记录。
2. 实现共享 JS / Rust 纯换算、原始日期校验、年度发生日和明确越界状态。
3. 接入模型、旧端保护、能力协商、备份和表盘，再接两端 UI。
4. 测两端所有日期往返、2033 闰十一月、年尾跨公历年、重复前/当日/次日、闰月回退、小月三十、表上界和无候选。
5. 测旧端修改、未知字段保留、恢复/写失败与排序/近期定位，最后测三屏 UI、release 包体增量及手环 9 性能。

### 可复现评估命令

```bash
# 离线：自洽往返、ICU 比较、锚点、范围和位表体积
node tools/evaluate-lunar.cjs

# 联网：额外核对固定上游和九个官方年表样本
node tools/evaluate-lunar.cjs --source --hko
```

评估工具位于 `tools/`，不被应用导入。运行时算法位于腕端 `dateUtils.js` 和插件 `lunar.rs`，使用修正版表而非原候选表。
